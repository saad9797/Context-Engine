The gaps that matter, ranked
1. GitHub PAT input is a trust and security problem, not just a UX one. Right now users paste a personal access token with full repo scope into your form. For a SaaS product this means: you're asking strangers to hand you a credential that can read and write to every private repo they own, you have to store it (encrypted, presumably — is it, currently? IngestionContext.data looks like it's stored as raw JSON in Postgres, meaning tokens saved via github_config would sit in plaintext in your DB), and there's no revocation path from your UI if a user's token leaks. The standard fix is a GitHub App (not OAuth App, not PAT): users install it on specific repos, you get short-lived installation tokens minted server-side, scoped to exactly what they granted, revocable from GitHub's side instantly. This is the single biggest "is this actually a SaaS product or a personal script" fork in the road.
2. Arbitrary connection strings = SSRF risk. postgres_url / mongo_url / storage credentials are taken directly from the request body and handed to pg/mongodb clients that will happily connect to 169.254.169.254 (cloud metadata endpoints) or any internal address if a malicious or careless user points them there — and your server does the connecting, from inside your infrastructure. You need an egress allowlist/denylist (block RFC1918 + link-local ranges unless explicitly on a "trusted" list) before any inspector dials out.
3. The subprocess is synchronous and blocking a web request thread with a 120s timeout. That's fine for a demo, not for a SaaS product — a large Postgres schema + a 500-file repo will blow past 120s, and even under it, you're holding a Django worker hostage per ingestion. This needs to become an async job: Django enqueues to Celery/RQ, returns 202 Accepted with a job ID immediately, Node runner reports progress, frontend polls or gets a websocket push. This also gives you retry-on-failure and per-tenant concurrency limits for free.
4. No tenancy boundary. IngestionContext has no visible user/organization FK — IngestionListView returns all saved contexts to any authenticated request. Every view needs .filter(user=request.user) (or org), and IngestionResultView/IngestionClaudeContextView need an ownership check before returning by pk, or any user can enumerate UUIDs and read someone else's schema + sample data.
5. context-filter.js is broken and silently falling back. You said it yourself — this is supposed to be the actual product deliverable (the distilled Claude-ready payload) and it's dead code right now, quietly replaced by a Python-side reimplementation (_build_fallback_claude_context) that's missing fields the JS version has (functions, indexed_columns, check_constraints, storage container details, codebase key_files_by_role content). Until this is fixed, the "give Claude exactly what it needs" promise isn't actually true for any live request — it's running the degraded fallback path on every single call, not just old records.
6. "Single interface to see whole architecture" isn't built yet — it needs a normalized graph, not four separate JSON blobs. Right now Postgres tables, Mongo collections, storage containers, and GitHub routes are four unrelated trees. A real "architecture view" needs one unified node/edge model — e.g. { nodes: [{id, type: 'table'|'collection'|'route'|'bucket', name, meta}], edges: [{from, to, kind: 'fk'|'references'|'uploads_to'}] } — built once at the end of ingestion, merging relationship_graph + storage_column_mapping + inferred route↔table connections. That's the actual product surface a frontend renders as a diagram.
7. No credential encryption at rest, no audit log, no rate limits/quotas per tenant. Standard SaaS table stakes once you're storing other people's DB passwords and API tokens: encrypt with a KMS-backed key (not app-level AES with a hardcoded key), log who ran what ingestion against what target and when, and cap ingestions/hour per plan tier so one user's runaway loop doesn't take down your Node runner pool.
